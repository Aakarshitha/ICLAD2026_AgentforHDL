Skill Overview

The VerilogSyntaxSanitizer skill is a defensive post-processing contract. It instructs agents to parse and clean their own generated Verilog code to comply with the standard Verilog-2005 compilation rules used by iverilog. This prevents common compiler errors like missing begin/end wrappers in task bodies, non-breaking space syntax corruption, and incorrect testbench signal types.

The Golden Reference Skeleton 

All generated or modified testbenches must conform strictly to the structure, variable placement, and syntax conventions demonstrated in this Golden Reference Skeleton:

// File Name: tb_<dutname>_<number>.v
`timescale 1ns / 1ps

module tb_<dutname>_<number> (); 
    // Note: Top-level testbenches typically have an empty port list () 
    // as they serve as the self-contained simulation environment.

    // ---------------------------------------------------------
    // 1. Signal & DUT Declarations
    // ---------------------------------------------------------
    // Inputs to the DUT are declared as 'reg' (driven by the TB)
    reg clk;
    reg rst_n;

    // Outputs from the DUT are declared as 'wire' (observed by the TB)


    // ---------------------------------------------------------
    // 2. Global Testbench Control & Tracking Variables
    // ---------------------------------------------------------
    // Declared at module scope to comply with Verilog-2005 rules
    integer error_count;
    integer local_errors;
    
    // Test configuration flags
    reg     RUN_ALL;
    reg     skip_basic_rw;
    reg     run_T101;


    // ---------------------------------------------------------
    // 3. Clock Generation Block
    // ---------------------------------------------------------
    parameter CLK_PERIOD = 10; // 100 MHz clock example

    always #(CLK_PERIOD/2) clk = ~clk;


    // ---------------------------------------------------------
    // 4. Design Under Test (DUT) Instantiation
    // ---------------------------------------------------------
    // Module name matches the IP exactly.
    // Instance name uses the strict 'uut_' prefix convention.
    <dutname> uut_<dutname>_<number> (
        .clk   (clk),
        .rst_n (rst_n)
    );


    // ---------------------------------------------------------
    // 5. Helper Tasks (IEEE 1364-2005 Compliant)
    // ---------------------------------------------------------
    // Rules:
    // - Must declare all inputs/outputs at the top of the task body.
    // - Must enclose multiple statements inside an explicit 'begin ... end' block.
    task bus_write;
        input [31:0] addr;
        input [31:0] data;
        begin
            @(negedge clk);
            $display("[TIME: %0t] [TASK] Bus Write -> Addr: 0x%h, Data: 0x%h", $time, addr, data);
            @(posedge clk);
            #1; // Wait for Non-Blocking Assignment settling
        end
    endtask

    task bus_read;
        input  [31:0] addr;
        output [31:0] rdata;
        begin
            @(negedge clk);
            rdata = 32'h0; // Placeholder assignment
            $display("[TIME: %0t] [TASK] Bus Read  -> Addr: 0x%h", $time, addr);
            @(posedge clk);
            #1;
        end
    endtask


    // ---------------------------------------------------------
    // 6. Helper Functions (IEEE 1364-2005 Compliant)
    // ---------------------------------------------------------
    // Rules:
    // - Cannot contain time control (no '#', '@', or 'wait' statements).
    // - Must contain at least one input.
    // - Must assign a value to the function name identifier before returning.
    // - Must wrap multi-statement operations in 'begin ... end'.
    function [31:0] compute_even_parity;
        input [31:0] raw_data;
        begin
            compute_even_parity = ^raw_data;
        end
    endfunction


    // ---------------------------------------------------------
    // 7. Stimulus Block (Initialization, Toggling & Tests)
    // ---------------------------------------------------------
    initial begin
        // A. Initialize all stimulus-driven signals and control registers
        clk           = 0;
        rst_n         = 0;
        error_count   = 0;
        local_errors  = 0;
        
        // Configure test run overrides
        RUN_ALL       = 1;
        skip_basic_rw = 0;
        run_T101      = 1;
        
        // B. Reset Toggle Sequence
        #(CLK_PERIOD * 2); 
        rst_n = 1;         // De-assert reset
        #(CLK_PERIOD * 5);

        // C. Apply Test Stimulus
        // --- T101: Basic Sanity Test ---
        if (!skip_basic_rw && (RUN_ALL || run_T101)) begin
            local_errors = 0;
            
            // Invoke the helper task
            bus_write(32'h0000_1004, 32'hDEADC0DE);
            
            // Example of using the helper function
            $display("[INFO] Parity of test payload is: %b", compute_even_parity(32'hDEADC0DE));

            // Set final grade tag matching the grader regex
            if (local_errors == 0) begin
                $display("[PASS] T101");
            end else begin
                $display("[FAIL] T101");
                error_count = error_count + 1;
            end
        end
        
        // D. End Simulation
        #(CLK_PERIOD * 10);
        $finish;
    end

endmodule


Agent Instructions & Reasoning Steps

When finalizing code outputs, you must run the generated code through this mental sanitizer step to enforce the following rules:

Step 1: Enforce Verilog-2005 Task wrapping

Standard Verilog-2005 requires that any task containing more than one statement must wrap its body in an explicit begin ... end block.

Inspect every task declaration you generate. If it contains multiple assignments or system calls, ensure it is formatted as shown in the Golden Reference Skeleton.

Strict Rule: Do NOT omit the begin and end statements inside task declarations. Doing so causes immediate Icarus Verilog compilation failures.

Step 2: Enforce Initial Begin-End Procedural Containment

All synthesized stimulus tests must be strictly contained inside a valid initial begin ... end procedural block to provide active simulation stimulus.

Every individual test scenario must begin with a commented-out header line declaring the target test number (e.g., // --- T101: Test Name --- or // --- T501 ---) immediately preceding the active transaction driver code.

Strict Rule: You must ensure that these sequential checks and their respective test number comment headers are entirely nested within the parent initial begin and end execution boundaries. This prevents stray statements from being parsed in the global module scope, which would trigger immediate compiler syntax errors.

Step 3: Prevent Invalid Port Directions in Testbench Module Bodies

Since tb_top is a top-level verification wrapper and does not contain an external port list declaration (declared simply as module tb_top; or module tb_top ();), standard input and output signals cannot have active input or output direction types assigned inside the module body.

You must change any invalid testbench-driven input port directions to reg, and any driven output port directions to wire (for example, input wire uart_rx must be declared as reg uart_rx and output wire uart_tx as wire uart_tx).

Step 4: Secure Strict Block Begin-End Conditional Alignments

Every category conditional checking block (if (!skip_basic_rw && ...)) wrapping multi-statement test routines must be explicitly opened with a trailing begin keyword and closed with a matching end keyword.

Strict Rule: You must never omit the begin statement on conditional blocks containing multiple test steps.

Step 5: Enforce Precise Indentation Alignment

The injected test code lines must match the indentation structure of the preceding line (such as the base comment // ── YOUR SANITY CHECKS HERE).

Ensure your generation matches this indentation block cleanly, avoiding stray hanging tabs or un-indented lines that break code readability.

Step 6: Scrub Stray Hallucinated Phrase Artifacts and Colons

Filter out non-code text blocks, stray colons, or un-commented header words (like : test_suite or descriptive non-verilog tags) from the code body. All documentation or block labels must be cleanly prefixed with standard comment slashes (//).

Verification checklist

[ ] Every multi-statement task body is wrapped in an explicit begin ... end block.

[ ] All test cases and their respective commented-out test number header lines are fully enclosed within a valid initial begin ... end block.

[ ] No SystemVerilog-specific keywords are present in the output.

[ ] No input/output port direction declarations exist inside the testbench body; all are converted to reg or wire.

[ ] The timescale directive resides on the absolute first line of the code file, prior to the module definition.

[ ] All conditional test structures are fully aligned with matching begin ... end blocks.

[ ] There are no unaligned indentation blocks or un-commented loose words inside the Verilog code block.
